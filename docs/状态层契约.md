# 状态层契约

> 一句话：每块状态各由谁生产、怎么派生、有几个副本，消费者只许读这里声明的字段。

状态层的唯一聚合实现是 `lib/state/contract.js`；本文件是它的可读视图。两边描述同一组事实 —— 字段名、类型、唯一生产者、派生方式、副本数。改字段先改 `STATE_BLOCKS`，再改这里的表：`test/state-contract.test.mjs` 逐行比对，两边漂了会红。

**同一声明处，两条响应**：`/dsh-purge/status` 把前五块摊平成一个信封；`/dsh-purge/health` 是另一条读面（安装指纹、预设副本比对与日志轨），字段同样声明在这里，形状判据同样是这里给的（`healthFieldReport`）。两条响应的字段表各是各的，比对逻辑是同一份。

## 1. 为什么把状态收成契约

同一个补丁状态原先有三个消费者各算一遍：`/dsh-purge/status` 写 `display_* ?? patches_*` 的回退、CLI 写 `patch_status[id] || "unknown"` 的补位、设置页与演练台各折一次层结论。三处都自洽，只是可能不是同一件事 —— 而「漂了」没有任何症状。

契约把「哪块状态、哪些字段、谁生产、怎么派生、几个副本」写成一张表。消费者只读字段，不再写算式。

三条边界，不满足就不是这份契约的实现：

- **纯聚合**：不读盘、不 import `lib/core.js`、不 import `lib/redteam/**`。输入由生产者交进来，聚合只做字段选择与计数。
- **不新增第二份派生**：计数、判据来源、待应用清单都只在契约里算一次。消费者重算一遍就是回归，`test/state-contract.test.mjs` 会点名。
- **副本数只减不增**：新增一份副本要在这张表里登记；评审时先收编副本，再谈加字段。

## 3. patch 块

`source` 是块级主判据，`sources` 是逐条来源。`source` 三值：

- `content`：判据来自字节 —— 写入清单加内容指纹，或自愈轮核对过的排除记录；
- `marker`：账本里还没有内容指纹（旧账本迁移前的那一轮），只能按痕量判；
- `override`：宿主未定位，补丁块只有注入文件状态可读。

`reasons` 只放设置类信息（例如安全阀还原），不改状态。「这条为什么判这样」要把 `sources` 与 `reasons` 一起读。

自愈轮不写 `node_modules/@…/lib/client.js`（写它会让 client-hmr 拿旧 rev 找脚本），所以这条路径没有 `written_files`。账本因此单列 `evidenceExcluded`：每条记补丁 id、记录时的补丁指纹、文件键、核对时的内容 sha256。读侧两样都对上才认 —— 正文换代或文件被动过，记录自动失效，回落到待应用。没有「核对通过」这一档时，宁可判待应用，也不拿 marker 当通行证。

| `reasons` | 映射：补丁 id 到字符串 | `lib/core.js` | trace | 3 |
| `status` | 映射：补丁 id 到状态字面量 | `lib/core.js` | content | 3 |

| `layers` | 对象：prompt / code / tool / unmapped | `lib/audit/layers.js` | content | 2 |

## 5. skills 块

技能目录的**唯一枚举实现**是 `lib/state/skills-catalog.js`：目录清单、优先级、库归属都在那里。两个读者（设置页的 `/dsh-purge/skills`、演练台的 `/redteam/api` 的 `skillCatalog`）只把结果摊成自己的字段名，不再各自扫目录。

两根目录就是 preset 的两行，顺序即优先级：

| 顺序 | 目录 | 库 | 何时出现 |
| --- | --- | --- | --- |
| 1 | `$DSH_HOME/skills` | `official` | 宿主原生技能的落点，用户自己那份 |
| 2 | `$DSH_HOME/redteam/skills` | `redteam` | 随包同步副本（启动时从包内 `skills/redteam` 同步；副本不存在时退回包内目录） |

**同名技能的显示规则**：按上表顺序取**先出现者**，落选的那份**不是重复项，是「被遮蔽的那一份」**。规则不是审美选择 —— 顺序反了，用户在自己那份里配好的地址与密钥会被随包模板（正文里是 `<你的VPS_IP>` 这类占位符）盖住，而两个页面都还「看起来完整」。因此 `shadowed` 要能数得出来、界面要说得出口，按库筛出来的子集也必须是**同一个集合**的子集（`filterByLibrary`），不是第二次枚举。

`items` 里的每一条带 `library`（`official` / `redteam`）与 `editable`（只有用户目录为真：随包副本是同步产物，改了会被下次同步盖回去）。`valid` 与 `error` 仍由各自的读者补：合法性判定要给编辑框看，可用性判定要给环境缺口看，两者都不改「目录里有哪些技能」。

| 字段 | 类型 | 生产者 | 派生 | 副本数 |
| --- | --- | --- | --- | --- |
| `dir` | 字符串：目录落点 | `lib/skills.js` | content | 2 |
| `source` | 字符串：读者来源 | `lib/skills.js` | content | 2 |
| `items` | 数组：条目 | `lib/skills.js` | content | 2 |
| `total` | 数字：总条数 | `lib/skills.js` | content | 2 |
| `fromPlugin` | 数字：本包技能数 | `lib/skills.js` | content | 2 |
| `invalid` | 数字：`valid` 为假的条数 | `lib/skills.js` | content | 2 |
| `byLibrary` | 对象：`official` / `redteam` 各几条 | `lib/state/skills-catalog.js` | content | 1 |
| `shadowed` | 数字：同名被遮蔽的条数 | `lib/state/skills-catalog.js` | content | 1 |

## 8. health 块

`/dsh-purge/health` 的三组字段（设置页的「健康」与「日志」两块只读）。它**是契约里的一块**，不是契约外状态：第一版把字段只写在 `test/settings-readonly-blocks.test.mjs` 的硬编码表里，于是加一个字段只要改测试就过，运行期没有任何东西会拒答 —— 那是「用测试代替声明」。

**为什么新增 `health` 块，而不是复用现有块（本批的二选一，选 a）**：

- 复用 `env` 会把两个问题搅成一件：`env` 答的是「演练台发送闸门的环境就绪度」（`platform-config` 的九个字段，生产者是平台配置），而 `install.*` 答的是「这棵插件树自己的文件与安装记录差在哪」（生产者是 `install-state` 的逐文件 sha256）。两者连失效方式都不同：前者是「没配工具路径」，后者是「包管理器不知道的手工改动」。
- 塞进 `STATUS_LEGACY_FIELDS` 等于给一条新响应在出生那天就开一份永久豁免。那张表的语义是「今天还在返回、下一轮收编」，是候车室不是家；也不存在「与它同构的新表」——再开一张同构表就是把「第五块之后随便开票」制度化，正是本批要收掉的那个口子。

**`presetCopy` 组为什么与 status 的 `preset` 块分开**：`preset` 块是痕迹派生（`preset-declare.json` 记「上一次注册走到哪一步」），`presetCopy` 是内容派生（仓库那一份与盘上那一份逐文件 sha256）。注册成功而副本停在旧版本是可能的 —— 两件事塞进一块，读的人迟早要猜「这条说的是哪一个」。

**两层判据**（`lib/state/contract.js` 的 `healthFieldReport`）：顶层键必须**恰好**是 `HEALTH_RESPONSE_FIELDS` 的五个（`ok` / `dsh_home` / `install` / `presetCopy` / `logs`），`install`、`presetCopy` 与 `logs` 组内的键必须**恰好**是本表声明的那些；两层的差额合成一张表，路径带组名（例如 `install.drifted`），端点回包前照它拒答（500）。比对逻辑与 `statusFieldReport` 是同一个 `keyDiff` —— 「同一份判据」指的是这件事，不是同一张表。

不做第三层：`logs.audit` 这类轨对象由各自的写侧函数整组产出，改一个键必然整组一起改；再往下拆，判据的维护成本会超过它拦得住的东西。

## 9. 契约外状态（`legacy_fields`）

全景里有四个状态**不在上面任何一块里**，但确实在盘上、确实被 `/dsh-purge/status` 或 CLI 读出去。它们不是「漏掉的字段」，是「还没收编的状态」：收编要动 `lib/core.js` 的判据段与 `lib/shim/**` 的写回，那是另一条轴。这里先把它们登记清楚 —— 生产者是谁、谁在读、为什么今天不收编。字段侧对应 `lib/state/contract.js` 的 `STATUS_LEGACY_FIELDS`。

| 状态 | 生产者 | 读者 | 为什么暂不收编 |
| --- | --- | --- | --- |
| `shim`（`shim_cmd` / `shim_ps1` / `shim_bin`） | `lib/shim/*.js` 写回、`lib/core.js` 判「内容是否等于原版」 | `/dsh-purge/status` 的 `shim_*` 三项、CLI `--status`、设置页 | 判据是「三个命令文件的内容 vs 原版」，属内容派生；收编要给它一个派生方式与副本清单，而动它必然碰到 `lib/core.js` 的判据段 |
| `install-state`（`$DSH_HOME/dsh-purge/install-state.json`） | `lib/install-state.js` 逐文件 sha256 | `bin/dsh-purge.js` 的诊断路径、`dsh_home` 的解析结果 | 它记的是「上一次安装时的逐文件指纹」，与补丁状态各算一份；收编前要先定「安装态与补丁态谁是真值」 |
| `host-backups`（`host-backups/<sha1>.bak`） | `lib/core.js` 动手前备份；**没有读侧**（只有 `has_backup` 这个布尔出了端点） | `/dsh-purge/status` 的 `has_backup` | 它是还原判据的输入而不是状态本身；`has_backup` 只是个布尔，收编成块要连还原侧一起改 |
| `cards`（`audit/cards/<戳>-<runId>.md`） | `lib/audit/handout.js` 的 `writeRunCard` | `audit why` 与 `audit check` 的读侧（本轮新补） | 卡是「这一轮值得回看」的落盘物，属审计轨的从属目录；收编进契约会把它抬成一个与 `audit` 平级的状态，而它没有独立生命周期 |

下面这些字段今天在响应里，但不在任何一块中。`STATUS_LEGACY_FIELDS` 与这张表逐条相同：

| 字段 | 现状 | 收编 |
| --- | --- | --- |
| `patches_lost` | 宿主重置后丢掉的补丁清单 | 下一轮收编：并入 patch 块 |
| `cliRepair` | shim 待修标记 | 下一轮收编：`lib/pending-status.js` |
| `autoApplied` | 启动自动 apply 的记录 | 下一轮收编：痕迹派生 |
| `shim_cmd` | 见上·`shim` | 下一轮收编：新增 `shim` 块后改成块字段 |
| `shim_ps1` | 见上·`shim` | 下一轮收编：同上 |
| `shim_bin` | 见上·`shim` | 下一轮收编：同上 |
| `has_backup` | 见上·`host-backups` | 下一轮收编：改为「还原判据可判 / 不可判」 |
| `override_status` | `prompt-inject.md` 的覆盖状态 | 下一轮收编：与 `override_path` 合并成一个块 |
| `override_path` | 同上，路径副本 | 下一轮收编：同上 |
| `dsh_home` | `$DSH_HOME` 的解析结果 | 下一轮收编：见上·`install-state` |

| 状态端点 | 五块全部（patch / audit / skills / env / preset） | `lib/index.js` 的 `/dsh-purge/status` |
| 健康端点 | health 块 | `lib/index.js` 的 `/dsh-purge/health` |
| 命令 / 工具 | patch 块 | `lib/index.js` 的 `/purge status` 与 `purge_status` |
| CLI | patch 块 | `bin/dsh-purge.js` 的 `--status` / `--diagnose` / `--apply` 收尾 |

新增消费者只许读契约字段。要「顺手算一下」的，先在 `STATE_BLOCKS` 加字段、在本文件登记，再改消费者 —— 顺序反了，下一个读者会看到两份不一样的数。

## 11. 演练台的只读 op（`/redteam/api`）

`/redteam/api` 是一条 POST 桥，同一个入口既接读也接写（`op` 决定）。收编只针对**读**那一半：它们回答的问题与 `/dsh-purge/status` 重叠（环境就绪度、技能目录、版本），各算一遍就会出现「同一个状态两个答案」，而两边都自洽。

**哪些算只读、为什么**（判据是「这条 op 会不会改盘上的状态」，不是名字像不像读）：

| op | 只读的理由 | 收编方式 |
| --- | --- | --- |
| `platformEnvAdaptStatus` | 只读 `config.json` + 探本机工具路径，写回一条都没有 | 回包 = 契约 `env` 块 + `ok`（`envAdaptPayload`） |
| `skillCatalog` | 只列目录、只跑可用性自检，不写技能文件 | 条目与计数走 `skills` 块（`skillsBlock`）+ 自己的信封（可用性摘要 / 分组 / 说明） |
| `skillRead` | 读一个技能文件 | 无块：单条正文，字段全在 op 信封里 |
| `platformConfigGet` | 只读 config 摘要（写是另一条 `platformConfigSave`） | 无块，但 `adapt` 那一段**是** env 块（`withEnvBlock`） |
| 事实库读类（`assets` / `stats` / `vulns` / `report` / `pocSearch` …） | `SELECT` 与计数，不写库 | 无块：领域载荷，只有信封键进表（`REDTEAM_STORE_ENVELOPE`） |
| `version` / `updateCheck` / `agentsStatus` | 只读版本与并发数 | 不进 `READONLY_OPS`：它们读的是包与注册表，不是状态层；字段留给各自模块 |

**判据**：`redteamOpReport(op, payload)` 把顶层键与「块字段 ∪ 该 op 的信封 ∪ 事实库信封」比一遍，多一个就报。`/redteam/api` 在回包出门前对 `READONLY_OPS` 里登记的 op 跑这一遍，不符就换成 `{ ok:false, error }`（运行期与 `test/api-parity.test.mjs` 是同一份判据）。

**写 op**：保留，但失败形状统一成 `{ ok:false, error }` —— `store-core.js` 的 `dispatch` 把任何异常收成这一形状，HTTP 层再把未捕获的异常收成 400 + 同一形状。来源校验（Origin / Host 同源）不动。

## 12. 认证矩阵：谁有资格说「这一版表已生效」

三次真机缺陷（自匹配假红、共享 marker 短路、already 永不被认证）长在同一个接缝上，修法却是一次一处。
这一节把它们钉成一张表：**marker 在不在、dry-run 有没有改动、账本认不认这条**，组合起来只有九种结论。
表进契约是因为它**是**判据 —— 单独改其中一格而不知道另几格，就是第四种形态的来源。

**三列的口径**（口径混用会让表自相矛盾，所以写在这里）：

- **marker 在文件里**：`patchApplied()` 在这个文件上命中。它是 fast path 的原料，不是结论。
- **dry-run 有改动**：**本轮 apply** 的 dry-run 会改文本吗。到了状态侧，「还有活」取决于它有没有被
  `patchesWritten` 消化：写过这一条的轮次已经把活干完（自匹配的补丁再点一次也不改文本），
  没写过就还在。所以第 4 行（有改动 + written）在状态侧是 `worked=false`，而第 3、8 行是 `worked=true`。
- **账本认证**：`patchesWritten` / `patchesSettled` 里有没有这条。**两者不是一回事**：`written` 说
  「这一版表真写过它」，`settled` 只说「核对的那一刻它就在目标态」，所以后者盖不住新的活（第 8 行）；
  旧账本两行指「逐补丁指纹整份缺失」：未迁移的放行一次，迁移后走真判据（第 7 行两半）。

| # | marker 在文件里 | dry-run 有改动 | 账本认证（written / settled） | 期望结论 | 依据 |
| --- | --- | --- | --- | --- | --- |
| 1 | 否 | 是 | 无 | pending | 原文还在，有活 |
| 2 | 否 | 否 | 无 | skipped | 原文对不上、点了也没有动作 |
| 3 | 是 | 是 | 无 | pending | marker 不证明活干完（共享 marker 借了别条的痕迹） |
| 4 | 是 | 是 | written | applied | 这一版表写过，且不再有差（自匹配收敛后） |
| 5 | 是 | 否 | written | applied | 正常已应用 |
| 6 | 是 | 否 | settled | applied | already 型（文件早在目标态、没有可写的字节） |
| 7 | 是 | 否 | 无（旧账本 / 无指纹） | applied（一次迁移）或 pending（迁移后） | 旧戳放行一轮，随后走真判据 |
| 8 | 是 | 是 | settled | pending | settled 只认证「当时就在目标态」，不许盖住新差 |
| 9 | 是 | 否 | 无（表指纹一致） | applied | 账本兼容路径：指纹在、两个清单都不含，靠内容自证（`patchCertifiedByContent`） |

**第九行与第七行不是一回事**：第七行的「无」指**连逐条指纹都没有**（旧账本，未迁移的放行一次、迁移后走真判据）；
第九行的「无」只指**两个清单都不含它**，逐条指纹是在的 —— 那一档来自 WP10→WP11 之间写下的账本（当时还没有
`patchesSettled`），只有内容自证能认证它：指纹一致 + marker 在 + 再点也不改文本（`patchCertifiedByContent`）。

**表外还有第四条轴：官方原文重放。** 上表三列说的都是「账本怎么说」，而有一条证据根本不读账本 ——
把**这一版表**重放到保险柜里的官方原文上，结果与现场逐字相同，即「这份文件就是这一版表的产物」。
它的位置在「没有 marker」之后、**「指纹不认」之前**：账本的逐条指纹与内容指纹都只是间接锚点，
且都会在补丁表换代后过期，让它们否决一份当场的重放证明，就是换宿主版本后第一轮收敛不了的根因。

这条轴的单位是**文件**，不是补丁：同一文件上后一条补丁会改写前一条的产物（id 84 在 id 83 插下的那段里
又插两行），按单条补丁重放与现场永远对不上。判据实现是 `lib/core.js` 的 `fileContentProof`，
载体是 `test/patch-round-converge.test.mjs`（用 id 83 / 84 的真正文构造，并带一条「现场只到半途 → 不许判
applied」的反例）。上表九行仍按账本三列成立：那一档的 fixture 没有官方快照，第四条轴无从发言。
少了这条兼容路径，升级之后的第一次启动会把这类补丁全报成待应用。表里第 1–3 行的「无」与第九行同义（两个清单都不含），
区别只在 dry-run 那一列 —— 还有活时内容自证不成立，所以它们是 pending。

**判据在哪里**：判据本体只有一处 —— `lib/patch/rollup.js` 的 `contentFileOutcome`（逐文件），
加上 `lib/core.js` 的两半证据（`patchTableTrusted` / `patchCertifiedByContent` / `patchFileTrusted`）。
九行逐行断言在 `test/patch-certify-matrix.test.mjs`，该用例同时核「本表与用例里的组合逐一对应」：
表里多一行、少一行、改一格，两边都会红。改判据请先改这张表，再改代码 —— 顺序反了，
下一个读日志的人会拿着旧表解释新结论。

**「账本认证」这一列现在包含两种记录，不只是「写过」**：

- `patchesWritten` / `patchesSettled`：补丁号清单，前者说「这一版表写过它」，后者说「核对的那一刻它就在目标态」；
- `evidenceExcluded`：**逐文件核对记录**，每条自带 `patchSha` / `file` / `contentSha`。写它的判据是
  「拿保险柜里的官方原文当底，把当前表的替换套一遍，结果与现场逐字相同」——它不读账本，
  所以**跨代表升级的那一轮**就能成立；读侧任何一项对不上就回落。

第二类是跨代收敛的关键：账本要等轮末才写得进去，而「文件早在目标态、没有可写字节」的补丁
只能靠认证才能进账本。少了这一条，跨代第一次 apply 永远判 pending、账本永远不写、第二次才收敛 ——
远端实测的「要跑两次 apply」就是这一条。它现在由每一轮 apply 对所有「没有可写字节」的文件产出，
不再只服务「不能写 client bundle」那一条旁路。
