# 0008. knip 盲区重议：根因更正，接受残余风险

> 一句话：盲区根因不是测试的动态 import，是探针脚本的；三文件具名，接受靠评审兜底。

- 状态：已接受（2026-10-24 S3 重议）
- 关联：`DELETE-2`；`docs/约束索引.md` 风险地图；0001 的后续
- 分工：本文留历史取舍；现行规则以 `docs/约束索引.md` 为准。

## 背景

0001 把盲区归因为「被测试文件动态 import() 的文件（core.js / atomic-fs.js 等）被 knip 判为不透明」，约定 S3 门禁收敛时重议。本轮实证推翻了该归因：

- `test/` 不在 knip 的 project 与 entry 里，测试文件的 import knip 根本看不到；把 `test/**/*.mjs` 加进 entry 再跑，盲区依旧（实测）。
- 真正原因：knip entry 里的两个只读探针脚本（`scripts/probe-host-patches.mjs`、`scripts/check-clean-host-sim.mjs`）动态 `import("../lib/core.js")`，knip 把动态导入的模块判为不透明、全部导出视为已引用。
- 盲区集合实测（HEAD 58aef6c，逐文件注入未用导出探针）：`lib/core.js`、`lib/desktop.js`、`lib/atomic-fs.js` 不红；对照组 `lib/host.js`、`lib/update.js`、`lib/surface.js`、`lib/audit/store.js` 等照红。

## 决策

候选修法逐一评估后，接受残余风险并更正登记：

1. 测试改静态具名 import——不针对根因（测试不在 knip 图里），且 `diagnostics-perf.test.mjs` 的冷路径技术（query 参数拿新模块实例）必须保留动态 import。否。
2. 给 knip 上游提 issue——不透明是文档化的保守行为，短期无解。否。
3. 文本死导出检查——误报面大（`lib/index.js` 的导出是给宿主的插件契约，仓库内零引用），且要养自己的白名单，正是 0001 / 0002 要消灭的豁免堆积。否。
4. 探针脚本改静态 import 且 `index.js` 的 `import * as core` 改具名——前者治不了 index.js 的命名空间导入，后者要动 2,829 行装配入口的导入形态，为门禁改它不值。否。

结论：盲区三文件在风险地图具名，新增未用导出靠评审兜底；ADR 0001 的归因以本篇更正。

## 后果

正面：根因与边界说准了——以后有人问「为什么 core.js 加导出不红」，答案从「测试动态 import」（错）变成「探针脚本动态 import + 命名空间导入链」（对）。

代价：残余风险不变——三个文件里的新死导出仍无机械覆盖。若将来真要覆盖，路径是决策 4，连同「改 index.js 导入形态」的代价一起认。
