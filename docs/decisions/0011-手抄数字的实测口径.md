# 0011. 手抄数字的实测口径：口径、窗口与致因提交

> 一句话：手抄数字必须带口径与窗口，且能按一条命令复算。

- 状态：已接受（2026-10-25 WP1，含一条「未取证」的显式登记）
- 关联：`REPO-1`；`test/docs.test.mjs`、`scripts/check-layout.mjs`；`docs/rebuild/08-closeout.md`
- 分工：本文留「数字怎么算才算数」的口径；具体数值以各文档当时的实测与 `scripts/measure.mjs` 为准。

## 背景

`docs/rebuild/08-closeout.md` 这个收尾快照里，8 处手抄数字与实测不符。逐项重做后发现它们**不是同一种错**，混在一起处理必然改错：

- 有的数字在文档写下的那一刻就与仓库对不上（`client-src` 的「18 文件 / 5,074 行」在三种计数口径 × 四个 revision 的任意组合里都不出现；「9 个超 800 行的模块」在任何 revision 上都数不出，豁免表一直是 11 行已排期 + 2 行永久）。
- 有的数字写的时候是对的，是**之后的提交把仓库改走了**（`client.js` 从 9,861 行变成 9,567；`/dsh-purge/*` 的 exact 路由从 14 条变成 15 条）。

两类若都「直接把数改成现在值」，第二类会让这份快照不再是任何一个真实版本的样子 —— 它记的是 `v2.0.0-release` 的坐标，而那些数字在自己的 tag 上是成立的。反过来，若两类都「只加一句注明时间」，第一类就永远错着，读者拿它当分母算覆盖率。

同一个坑还出现了三次，每次都出自「没写口径」：

- 上级交办的前提写「窗口是 3 个提交」与「(a) 3 / (b) 5」。实测窗口是 20 个提交、分类是 (a) 2 / (b) 6 —— 前一个数取自「离 HEAD 最近的三个提交」，后一个是按错误窗口算出来的。
- `:49` 的口径列写「`lib/redteam/ui.js` 与 `lib/index.js` 的注册表」，数值却只覆盖 `/dsh-purge/*` 一族（全部在 `lib/index.js`）。按口径列读会把 `ui.js` 的 `/redteam/api` 并进合计，得出 15 → 16 这个不存在的数。**口径列与数值不一致本身就是一处待修**，它比数值错更危险，因为它会主动把人引到错的读法上。
- 「`skills.js` 381 行」指的是 `lib/client-src/settings/skills.js`（现 360 行），不是 `lib/skills.js`（748 行，窗口内一笔提交都没碰过）。同名不同路径，指错对象会让「超限待切」的结论落到一个从未超限的文件上。

## 决策

1. **行数只有一条公式**：`node -e "console.log(require('fs').readFileSync('<f>','utf8').split('\n').length-1)"`。不用 `Measure-Object -Line`（不统计空行），不用 PowerShell `Get-Content`（把字符串字面量里的孤立 `\r` 也当换行）。历史端用同一公式跑 `git show <rev>:<path>`。
2. **窗口算法写死**：基线 = 该文档最后一次被触碰的提交，若它与某个 tag 同一状态就用那个 tag（判据 `git merge-base --is-ancestor` 与 `git log --oneline <触碰提交>..<tag>` 为空）；窗口 = `git log --oneline <基线>..HEAD`，逐项致因用 `git log --oneline <基线>..HEAD -- <该项的确切路径>`。
3. **同名文件一律写死完整路径**。只写裸文件名等于没写对象；文档里凡出现可能同名的片段（`skills.js`、`client.js`、`ui.js`）都必须带目录前缀。
4. **(a)/(b) 分类法**：窗口内没有任何提交碰过该项路径而值与文档不符 → **(a) 当时就写错**，直接改写；被碰过且基线值 = 文档值 → **(b) 之后被写旧**，保留原值并写明致因提交。判据是 `git log` 的路径过滤，不是回忆。
5. **(b) 项不改成现在值**，改为「值 + 现状 + 致因提交」。理由：这类文档是版本坐标，改成现在值就同时失去「那个 tag 是什么样」与「谁让它变的」两条信息。
6. **口径列必须写出三件事**：量的是哪一族（`/dsh-purge/*` 而不是「注册表」）、含不含边界成员（`lib/client-src` 含不含 `shell.js`）、算文件还是算行。口径说不清时，先按边界成员两种口径各量一遍再决定登记哪个。
7. **不权威的版本号不写**：见下节。

### `engines.node` 的未取证项

`package.json` 声明 `engines.node: ">=18"`，而 `lib/redteam/store.js:18` → `store-core.js:9`、以及 `store-core.js:37` → `schema.js:4` 都**静态** `import { DatabaseSync } from 'node:sqlite'`。该内置模块在 Node 18 / 20 上不存在，加载期就抛 —— 即这个声明写下的那一刻起就不成立。

真实下限是多少，本机量不出来：探测命令与结果如下。

```
where.exe node            → C:\Program Files\nodejs\node.exe   （全机仅此一个）
node -v                   → v24.20.0
node -e "require('node:sqlite')"  → 通过（v24.20.0）
nvm list                  → 命令不存在
Get-ChildItem 'C:\Program Files\nodejs','C:\Program Files (x86)\nodejs','C:\nvm'  → 无其它版本目录
```

本机只有 v24.20.0，没有 18 / 20 / 22 的任何一份可测，且 `schema.js:43-46` 自述 FTS5 支持随 Node **patch** 版本变化（22.14 无、22.23 有）—— 真实下限比「≥某个 minor」更细。故该字段**保持原值不动**，本文只登记「它不成立」这个事实与「下限未取证」这个状态，判据留给复核轮：谁核（复核会话）、核什么（一次跨版本实测，跑 `node -e "require('node:sqlite')"` 逐个版本记录）、核不出来时的后果（沿用现值，则旧 Node 上首屏即崩）。

该字段当前**无门禁载体**：对 `package.json`、`.github/workflows/*.yml`、`test/workflows.test.mjs` grep `engines`，只命中声明自身一处 —— 改错不会红，改对也不会绿。

## 后果

正面：数字从此分两类记账，历史快照保住「那个 tag 是什么样」，写错的数字不再被当成基线。口径列与数值必须自洽这一条，拦住的是一类会把人主动引到错读法的错误 —— 本轮就是被它坑过一次的。

代价：每轮收尾快照都要重新核一次致因提交，`(b)` 项会让读者多跳一步（值在表里、现状在口径列）。这是有意的取舍：快照的价值在于「当时」，不在于「永远最新」。

遗留：`engines.node` 是一条**已知不成立但未取证到正确值**的声明，且没有门禁守着它。这条必须由一次跨版本实测闭环，不许按「大概率是 22」推一个数填进去 —— 那正是本轮在修的那类错。
