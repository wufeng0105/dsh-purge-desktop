# 0013. 三轨失败语义同表：诊断轨 / 审计轨 / 设置页对同一条补丁给同一结论

> 一句话：补丁状态的三种读法收口到一张表，失败不再被算成跳过。

- 状态：已接受（2026-10-25）
- 关联：`lib/patch/status.js`（唯一权威）；`lib/audit/report.js`；`lib/audit/layers.js`；`lib/layer-rows.js`；`lib/core.js`；`test/patch-status.test.mjs`；`test/audit-apply-entries.test.mjs`

## 背景

同一份补丁判定被三处读：

1. **诊断轨**（`lib/core.js` 的 `summarizeApplyReport` / `applyEndCounts`）：决定 `apply.host` / `apply.end` 的 `failed` 计数；
2. **审计轨**（`lib/audit/report.js` 的 `recordApply` 与 `lib/audit/layers.js` 的 `summarizeLayers`）：决定层结论的 `result` 与 `failed` / `skipped` 计数；
3. **设置页**（`lib/layer-rows.js` + `lib/core.js` 的 `groupPatchesForDisplay` / `tallyDisplayPatches`）：决定状态点色调与「跳过 / 失败」的计数。

收口前有两类偏差：

- **`pattern_not_found` 的软硬只有诊断轨知道**。补丁声明 `onMiss: warn / ignore` 时诊断轨按「这一版不需要」放过，而审计轨拿不到补丁对象、一律算失败；设置页的分组则按状态字符串现判。
- **失败组在设置页被算成跳过**。分组结论的 else 分支把 `read_error` / `write_error:…` / 硬 miss 都归到 `skipped`，于是摘要行显示「跳过 N」、状态点是 idle —— 看起来像没事。

## 决策

三处都消费 `lib/patch/status.js` 的同一组函数，不再各写一句 `if (status === …)`：

- `isSoftOk(row, patch, resolveOnMiss)`：补丁级软硬（`strictFiles` 优先，其次 `onMiss`）；
- `resultOfStatus(status, { softOk })`：审计轨的三态折算；
- `isReady(status, patch, resolveOnMiss)`：列表上的「已就绪」，引擎的 `patchStatusReady` 直接转发它；
- `displayBucketOf(status)` / `toneOf(status)`：设置页的归桶与色调。

`pattern_not_found` 要按补丁声明分两行看 —— 这是本表唯一需要第二列的原因，不是两种口径。

## 补丁状态 → 三轨结论

| 补丁状态 | 补丁声明 | 诊断轨（`apply.patch` → 汇总） | 审计轨（层结论 / 文件行） | 设置页（色调 / 计数） |
| --- | --- | --- | --- | --- |
| `read_error` | 任意 | `failed` + `readError` 各 +1 | `fail`（`{层}.patch-miss`，`detail.status` 留原值） | `error` / 失败 +1 |
| `write_error:<底层错误>` | 任意 | `failed` + `writeError` 各 +1 | `fail`（`{层}.patch-miss`） | `error` / 失败 +1 |
| `failed` | 任意 | `failed` +1 | `fail`（`{层}.patch-miss`） | `error` / 失败 +1 |
| `pattern_not_found` | `onMiss` 缺省或 `fail`，或 `strictFiles: true` | `failed` +1，`notFound` +1 | `fail`（`{层}.patch-miss`） | `error` / 失败 +1 |
| `pattern_not_found` | `onMiss: warn / ignore` 且非 `strictFiles` | 不进 `failed`（记 `soft`），`notFound` 仍 +1 | `skip`（`{层}.patch-skipped`） | `idle` / 跳过 +1 |
| `applied` | 任意 | 进 `applied` / `soft` | `ok`（`{层}.patch-applied`） | `ok` / 已做 +1 |
| `already` | 任意 | 进 `already` / `soft` | `skip` | `ok` / 已做 +1 |
| `skipped` | 任意 | 进 `soft` | `skip` | `idle` / 跳过 +1 |
| `missing_file` | 任意 | 进 `soft`，不算失败 | `skip` | `idle` / 跳过 +1 |
| `off` | 任意 | 进 `soft`，不算失败 | `skip` | `idle` / 跳过 +1 |
| `na` | 任意 | 不进统计 | `skip` | `idle` / 跳过 +1 |
| `pending` | 任意 | 不由 apply 产出 | 不由 apply 产出 | `idle` / 待应用 +1 |
| `deferred` | 任意 | 不由 apply 产出 | 不由 apply 产出 | `idle` / 跳过 +1 |

「诊断轨的结论档位」指两件事：`status` 本身（第一列）与它进不进 `apply.end.failed`。表里四类失败输入（`read_error` / `write_error:…` / `failed` / 硬 `pattern_not_found`）在诊断轨都进 `failed`，在审计轨都是 `fail`，在设置页都是 `error` —— 三处同一结论。

## 判据与载体

- 表驱动：`test/patch-status.test.mjs` 对每个 status × 每种补丁声明断言 `patchStatusReady` 与 `isReady` 同结论，并锁 `resultOfStatus` 的 `softOk` 只影响 `pattern_not_found`。
- 分组与计数：同一文件的 `rollupDisplayStatus` / `tallyDisplayPatches` 用例锁「失败组自成一档、不进跳过、不算就绪」。
- 两轨落账：`test/audit-apply-entries.test.mjs` 用同一批判定同时喂审计轨与诊断轨，断言硬 miss 只让两边各有一条失败、软 miss 两边都放过。
- 改这张表等于改日志口径：`lib/patch/status.js` 的五行快照由 `test/patch-status.test.mjs` 逐字守护，改口径必须同时改那处快照并在本文件留档。

## 已知限制

- 设置页的摘要「失败数」在客户端仍只数 `patch_status` 里的 `unmatched`（`lib/client-src/settings/page.js`）；服务端新增的 `patches_failed` 字段已给出同一口径的失败数，客户端要不要改读它不在本决定的范围。
- 旧日志（本决定之前写的审计行）里 `pattern_not_found` 一律是 `fail`。读旧日志要按当时的规则重算，别把它当成本轮的矛盾。
