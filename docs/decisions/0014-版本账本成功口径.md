# 0014. 版本账本的成功口径：三档门槛、无改动轮自陈、密封分支已知缺口

> 一句话：版本账本只记成功收尾；无改动轮自陈，密封分支缺口登记在案。

- 状态：已接受（2026-10-26）；2026-10-27 追加分层（见文末「修订」）
- 关联：`lib/reapply.js`（`isCleanApplyRound` / `markPatchesApplied` / `noteAppliedAudit`）；`bin/dsh-purge.js`（CLI 成功尾）；`lib/index.js`（HTTP 的 `complete`）；`test/audit-apply-entries.test.mjs`；`docs/约束索引.md` 的 `AUDIT-4`

## 背景

`applied.json` 是版本账本：`run_id` 回答「最后一次**成功** apply 是哪一轮」，`audit` 块是那一轮的审计摘要（`events` / `layers` / `unresolved`）。这台机器上曾经出过两种错法：

1. **CLI 不写账本**：`markPatchesApplied(..., { runId })` 只有面板 HTTP 那条路调用。CLI 成功 apply 之后，账本里留的还是上一轮，`startup.ready.appliedRunId` 因此对不上刚跑完的那一次。
2. **CLI 把失败轮写进账本**（V2 抓到的硬错）：只要命令走到收尾就写，`failed` / `read_error` / `write_error` 的部分失败轮也会占住 `run_id` —— 账本把「最后一次**尝试**」写成了「最后一次成功」。

修法把判据收成一处：`reapply.isCleanApplyRound({ failed, hostWritten, hookDenyRestoreFailed })`，CLI 与面板共用同一组输入。本轮把这条口径与它剩下的两个语义问题（无改动轮、密封分支）定下来，不改运行行为。

## 决策

### 一、成功收尾三档，CLI 与 HTTP 同源

账本只在下面三档全过时写：

| 档位 | 判据 | 来源 |
| --- | --- | --- |
| 硬失败为零 | `summarizeApplyReport(report).failed.length === 0` | `lib/reapply.js` 的 `isCleanApplyRound`（`failed`） |
| 清洗标记真的落到宿主上 | `allPatchHostsWritten(hosts)` 或 `hostCleanMarkersPresent(首宿主 · 状态里的 aiBase)` | 同上（`hostWritten`） |
| 安全阀还原没有失败 | `hookDenyRestoreFailed` 为空 | 同上（`hookDenyRestoreFailed`） |

面板那条路（`lib/index.js` 的 `complete`）本来就是这么判的，另外还要求 `flash.ok`。CLI 的 `isCleanApplyRound` 不把 `flash.ok` 当门槛：`cmd-flash` 在 CLI 上是信息项（打在输出与 `cli.apply.done.flash_ok` 里），它与「补丁有没有写进去」不是同一件事。**这是口径，不是遗漏**；密封分支因此留下的一档差异见本文件的「三」。

**软失败不进 `failed`**：`pattern_not_found` 在补丁声明 `onMiss: warn` / `ignore` 且非 `strictFiles` 时按「这一版不需要」放过；`missing_file` / `off` / `skipped` / `already` 同样不进 `failed`。这与 `docs/decisions/0013-三轨失败语义同表.md` 的对照表是同一口径 —— 三轨与账本对同一个状态给同一个结论。

### 二、无改动 / 缺件轮：成功但自陈（对应账本条目 E11）

`missing_file` 与 `notFound` 是软档：目标文件在这台宿主上本来就不存在，或 pattern 这一版不需要。这类轮可以满足上面的三档（`failed=0`、`hostWritten` 为真），于是**会写账本**，即使 `applied=0`、三层结论全是 `skip`。

这是有意的：**它是「成功的无改动轮」，不是失败轮**。理由有三条：

1. 口径不能只看 `applied>0`。干净、已对齐的宿主再 apply 一次全是 `already`（`applied=0`）—— 那是这台机器上最常见的形态，把它判成「不算成功」会让 `appliedRunId` 停在更早一轮，读者反而以为最近这次没跑成。
2. 它**自陈**了没改东西：账本的 `audit.layers`（逐层 `result`）、`audit.unresolved`，加上诊断轨 `apply.end` 的 `missingFile` / `applied`，三处一起说明「这一轮一条都没写」。读 `appliedRunId` 时先看这三样，不要把它读成「这一轮改了东西」。
3. 改口径的代价更大：要么让无改动轮不刷新账本（`applied` 与 `already` 的判定要重写），要么把 `missingFile` 拉进硬失败（缺件宿主永远记不成成功）。HTTP 与 CLI 必须同改，`startup.ready.appliedRunId` 的语义也跟着变 —— 那是新条目，不是固化该做的事。

**结论**：`appliedRunId` 指向一轮「无改动但成功」的 apply 是口径内的事，不是 bug。要回答「最近一次**改了文件**的 apply 是哪轮」，去看那一轮账本的 `audit.layers` 与 `apply.end.missingFile`，不要指望 `run_id` 单独给答案。

### 三、密封分支的 `hookDenyRestoreFailed` / `flash.ok`：已知缺口（对应账本条目 E10）

密封路径走 `core.ensureHostClean`，它的返回面是 `{ok, aiBase, pending, hosts, report}` —— **没有 `hookDenyRestoreFailed`**（那个字段在它内层调用的 `applyPatchesAllHosts` 里）。所以 `bin` 在密封分支上只能把它当空值，`isCleanApplyRound` 的第三档在那一档是「没有报告」，不是「验证通过」。

现在挡在它前面的是 `cleaned.ok`：`ensureHostClean` 在「还有待清洗项 / 有硬失败（`pattern_not_found` 除外）/ 某宿主 `flash.ok` 不为真 / 标记没写进全部宿主」任一成立时返回 `ok:false`，CLI 在那之前已经 `exit 1`。剩下的差异只有一档：**安全阀还原失败、但其余三档都过**时，密封 CLI 会把这一轮写进账本，而面板那条路不会。

要把这一档也逐字对齐，得给 `ensureHostClean` 的返回补 `hookDenyRestoreFailed` —— 那是 `lib/core.js` 的返回面，属引擎冻结区，本阶段不动（E10 登记为「提出」，风险地图里也列了这一条）。`flash.ok` 同理：它在密封路径上由 `ensureHostClean` 自己当门槛用，CLI 的账本门槛不重复要求，写清为口径。

## 判据与载体

- 门槛本身：`lib/reapply.js` 的 `isCleanApplyRound`。输入缺省按「没洗干净」处理（`failed` 非整数记 0、`hostWritten` 必须显式为 `true`、`hookDenyRestoreFailed` 只接受假值），不许默认放行。
- 接线与正反两向：`test/audit-apply-entries.test.mjs` —— 门槛矩阵（硬失败 / 缺标记 / 安全阀失败为假，软失败为真，缺输入与 `null` 为假）、失败收尾后 `applied.json` 逐字节不变、`bin` 的判定→写戳→并摘要顺序与三档输入齐全。
- 条文与载体：`test/constraint-index.test.mjs` 锁 `AUDIT-4` 的条文关键词（`isCleanApplyRound` / `failed=0` / `hostWritten` / 无改动 / 已知缺口）与三个载体都存在。
- 远程验收（WP4 的 C27–C29，已通过）：干净 CLI 轮写 `run_id` + `audit`、完整重启后 `startup.ready.appliedRunId` 对齐；独占锁造出的硬失败轮 `applied.json` 逐字节不变、`run_id` 仍是上一轮成功、输出有「版本账本未更新」。

## 已知限制

- `appliedRunId` 包含无改动轮（本文件「二」）。要「最近一次真的改了文件的 apply」得看账本的 `audit.layers` 与 `apply.end.missingFile`。
- 密封分支的 `hookDenyRestoreFailed` 恒为「没有报告」（本文件「三」）；逐字对齐要动 `lib/core.js`。
- CLI 的 `flash.ok` 不是账本门槛，只是信息项。面板那条路是门槛 —— 两条路在这一点上不同义，这是有意为之。
- 「版本账本未更新（failed=… hostWritten=…）」只在 CLI 的 stdout 上，没有落成诊断轨事件：新事件/新字段要同步世代表与读法，属新条目。失败的事实本身两轨都有（`apply.end.failed`、审计层结论）。

## 修订（2026-10-27）：账本分两层，事实每轮都写，身份只记干净轮

原文把两件事写成了一件：「账本只在成功收尾时写」。真机暴露出这条口径的副作用 ——
**任何一条 pending 都能把自己锁死**：pending 让这一轮不干净，不干净就不写账本，
不写账本下一轮仍认证不了那一条，于是跨代升级要跑两次 apply（第一次的 pending 永远是那三条）。

现在分两层，落点在 `lib/stamp.js`（版本账本从 `lib/reapply.js` 搬出，`reapply` 只转出 API）：

| 层 | 内容 | 什么时候写 |
| --- | --- | --- |
| 事实 | `tableSha` / `patchShas` / `patchesWritten` / `patchesSettled` / `evidenceExcluded` / `contentSha` / `hostVersion` / `lastRound` | **每一轮** apply（干净与否都写） |
| 身份 | `run_id` / `audit` | 只有三档全过的干净轮 |

`isCleanApplyRound` 的判据一个字没改，它现在只决定「身份写不写」，不再决定「事实写不写」。
CLI 收尾因此变成：先算 `cleanRound`，再 `markPatchesApplied(..., { runId: cleanRound ? applyRunId : "", round })`；
不干净时 stdout 仍会说清是哪一档没过，措辞改为「账本记了本轮事实，但『最后一次成功 apply』仍指向上一次」。

配套的第二处改动在判据侧：`apply(当前表, 官方原文) === 现场字节` 这条核对记录（`evidenceExcluded`）
现在对**所有**「没有可写字节」的文件产出，不再只服务 client bundle。它不读账本，所以跨代那一轮就能成立 ——
两个改动合起来才是「单次 apply 收敛」；少了任一半，账本要么不写、要么写了也没证据。

判据：`test/cross-generation-converge.test.mjs`（红灯：旧账本 → pending；绿灯：单次 apply → 落账 → applied）、
`test/audit-apply-entries.test.mjs`（事实每轮写、run_id 只记干净轮）。
